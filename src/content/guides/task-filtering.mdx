Give the task list three views: **All**, **Active**, and **Completed**. You'll
build the change in three runnable stages, then add tests for the behavior.
No new packages are needed.

## Start from the working screen

Finish the [quickstart](/quickstart) first. Work in
`examples/expo-task-starter`. The committed starter has completion controls
but no filters; this guide adds them in your local copy.

Open `App.tsx` in your editor. Its `App` function is the screen component.
The `tasks` state holds the task objects, and `toggleTask` changes one task's
completion status. Keep that handler unchanged throughout the guide.

Keep `npm start` running in one terminal. Open a second terminal at the
repository root and run:

```sh
cd examples/expo-task-starter
npm run typecheck
npm run lint
npm test
```

These check TypeScript types, lint rules, and automated behavior respectively.
You should have **one passing suite and four passing tests**. Keep the original
`__tests__/App.test.tsx`: every stage below should preserve those behaviors.
Run later commands from this same example directory.

## 1. Make the filter controls respond

Start with the choice itself. React's `useState` remembers a value between
renders; its setter changes that value and asks React to render again. You'll
use it to show which control is selected before changing the task list.

### Add the options and selection

In `App.tsx`, add this after the existing `Task` type and before `initialTasks`:

```tsx
type Filter = 'all' | 'active' | 'completed';

const filters: { value: Filter; label: string }[] = [
  { value: 'all', label: 'All' },
  { value: 'active', label: 'Active' },
  { value: 'completed', label: 'Completed' },
];
```

`Filter` is a TypeScript union: the value must be one of those three strings.
The annotation on `filters` describes an array of objects with a typed `value`
and a text `label`. It catches misspelled choices while keeping the visible
labels separate from their lowercase values.

Immediately after the existing `tasks` state declaration inside `App`, add:

```tsx
const [filter, setFilter] = useState<Filter>('all');
```

`filter` is the current choice; `setFilter` changes it. `'all'` is the initial
value. The `<Filter>` annotation tells TypeScript which choices are allowed.
Keep this call at the top level of `App`, beside the existing `useState` call,
so React can associate each state value with the component consistently.

### Render the controls and their styles

The starter uses `FlatList` to render task rows from an array. Its
`ListHeaderComponent` prop supplies content above those rows. Inside that
header, insert this `View` after the description's closing `</Text>` and
before the header's closing `</View>`:

```tsx
<View style={styles.filters}>
  {filters.map((option) => (
    <Pressable
      key={option.value}
      accessibilityRole="button"
      accessibilityLabel={option.label}
      accessibilityState={{ selected: filter === option.value }}
      onPress={() => setFilter(option.value)}
      style={({ pressed }) => [
        styles.filterButton,
        filter === option.value && styles.selectedFilter,
        pressed && styles.pressedFilter,
      ]}
    >
      <Text
        style={[
          styles.filterLabel,
          filter === option.value && styles.selectedFilterLabel,
        ]}
      >
        {option.label}
      </Text>
    </Pressable>
  ))}
</View>
```

`map` creates one control for each option. The `key` gives each one a stable
identity. `onPress` receives a function that calls `setFilter` when you tap;
it doesn't call the setter while the screen is rendering. The equality check
`filter === option.value` identifies the selected option.

`Pressable`, `Text`, and `View` are already imported. Each control exposes a
button role, label, and selected state to accessibility services. Visible
styling also needs to show the choice; color alone isn't enough.

Add these entries inside the existing `StyleSheet.create({ ... })` object,
before its closing `});`. Keep all existing entries:

```tsx
filters: { flexDirection: 'row', flexWrap: 'wrap', gap: 8 },
filterButton: {
  minHeight: 48,
  minWidth: 48,
  justifyContent: 'center',
  alignItems: 'center',
  paddingHorizontal: 16,
  paddingVertical: 12,
  borderWidth: 2,
  borderColor: '#CBD3D8',
  borderRadius: 10,
  backgroundColor: '#FFFFFF',
},
selectedFilter: { borderColor: '#246247', backgroundColor: '#EDF5F1' },
pressedFilter: { opacity: 0.75 },
filterLabel: { fontSize: 16, color: '#172126' },
selectedFilterLabel: { fontWeight: '700' },
```

The `style` callback receives whether the control is being pressed. In its
array, `condition && style` includes that style only when the condition is
true. The selected control has a green border, tinted background, and heavier
text. Controls can wrap and grow with larger text; their minimum height of
48 logical units keeps the press target usable without fixing the row height.

### Check the selection before filtering

Save `App.tsx`. In the Metro terminal, press `r` for a full reload. **All**
should start selected. Press **Active**, then **Completed**: the selected
styling should move, but **all three tasks should still be visible**. That's
the intended checkpoint; the next step will connect the choice to the rows.

In the second terminal, run:

```sh
npm run typecheck
npm run lint
npm test
```

All checks should pass, including the original four tests. If the controls
don't appear, check that the new `View` is inside `ListHeaderComponent`. If a
style name is missing, check its spelling and that it is inside
`StyleSheet.create`. Don't move on until selection changes correctly.

## 2. Show only the matching tasks

Now use the choice to calculate the visible rows. JavaScript's `filter`
method builds a new array containing items for which its callback returns
`true`. It doesn't remove items from the original array.

After the `filter` state declaration, before `toggleTask`, add:

```tsx
const visibleTasks = tasks.filter((task) => {
  if (filter === 'active') return !task.completed;
  if (filter === 'completed') return task.completed;
  return true;
});
```

For Active, `!task.completed` keeps unfinished tasks: `!` reverses a boolean.
For Completed, keep finished tasks. For All, return `true` for every task.
This is a derived value: calculate it from the current tasks and choice on
each render instead of keeping a second array in state. Three tasks don't
need memoization or an effect to keep two lists synchronized.

In `FlatList`, replace `data={tasks}` with:

```tsx
data={visibleTasks}
```

`data` is the array the list displays. Leave `keyExtractor` and `renderItem`
unchanged: they still identify and render each task. This implementation
passes a new derived array on each render, so it doesn't need `extraData`.

### Check the lists and a changing task

Save and reload, then select each filter:

| Filter | Expected initial rows |
| --- | --- |
| All | All three tasks |
| Active | Run the app on your phone; Mark a task complete |
| Completed | Explore the starter code |

Select **Active** and complete **Run the app on your phone**. It should
leave Active immediately. Select **Completed** to find it checked there,
then reopen it. It should leave Completed and reappear in Active.

The task wasn't deleted: its status stopped matching the current view.
`toggleTask` must still update the full `tasks` array. Mapping over only
`visibleTasks` would lose tasks hidden by the filter.

Run the checkpoint checks again:

```sh
npm run typecheck
npm run lint
npm test
```

The original four tests should still pass because All remains the default.
If every filter shows three rows, check the `data` replacement. If the first
screen or original tests show fewer rows, check the initial filter is `'all'`.
An empty filter currently shows no task rows; next you'll give it an explanation.

## 3. Explain an empty view

Completing the last active task shouldn't leave the reader wondering whether
the app stopped working. Give each empty view a message, with the controls
still available to switch back to All.

After the `visibleTasks` calculation and before `toggleTask`, add:

```tsx
const emptyMessage =
  filter === 'active'
    ? 'No active tasks. Everything is complete.'
    : filter === 'completed'
      ? 'No completed tasks yet.'
      : 'No tasks to show.';
```

This conditional expression chooses a message from the current filter. Read
it as: if Active, use the first message; otherwise, if Completed, use the
second; otherwise, use the final message. The All fallback is defensive:
this fixed starter has no way to remove every task.

Add this prop to `FlatList` immediately after `data={visibleTasks}`:

```tsx
ListEmptyComponent={
  <Text style={styles.emptyMessage}>{emptyMessage}</Text>
}
```

`ListEmptyComponent` renders when `data` has no items. Add its style inside
the existing `StyleSheet.create` object:

```tsx
emptyMessage: { fontSize: 17, lineHeight: 26, color: '#46545C', paddingVertical: 20 },
```

### Check both empty states

1. Save and reload. Select **Active**, then complete **Run the app on your
   phone** and **Mark a task complete**. Each row should disappear. Expect
   **No active tasks. Everything is complete.** Return to **All**: all three
   tasks should still exist and be complete.
2. Reload to restore the initial tasks and All selection. Select **Completed**,
   then reopen **Explore the starter code**. Expect **No completed tasks yet.**
   Return to **All**: all three tasks should be present and incomplete.

The header stays visible even when there are no rows. Keeping its controls
inside the scrolling list also lets the screen accommodate larger text.
If you see a blank list without a message, check that `ListEmptyComponent`
is a prop on `FlatList` and that its style name matches.

Run the checkpoint checks:

```sh
npm run typecheck
npm run lint
npm test
```

You should still have four passing tests. Those protect the starter's
behavior; next you'll add tests specifically for the feature you've built.

## 4. Turn those checks into tests

The project already includes Jest and React Native Testing Library. A test
renders the screen, finds controls by their accessible role and label, acts
on them, and checks the visible result. This exercises the interface rather
than calling a filtering function in isolation.

### Confirm the initial selection

Create `__tests__/Filtering.test.tsx` beside `App.test.tsx` with these complete
contents:

```tsx
import { render, screen } from '@testing-library/react-native';
import App from '../App';

test('starts on All and exposes the selected filter', async () => {
  await render(<App />);
  expect(screen.getAllByRole('checkbox')).toHaveLength(3);
  expect(screen.getByRole('button', { name: 'All', selected: true })).toBeOnTheScreen();
  expect(screen.getByRole('button', { name: 'Active', selected: false })).toBeOnTheScreen();
  expect(screen.getByRole('button', { name: 'Completed', selected: false })).toBeOnTheScreen();
});

```

`render` creates a test instance of the screen. `screen` queries that instance;
`expect` checks the result. The `selected` query verifies the accessibility
state exposed by the button, not just the presence of its label. The async
function and `await` let the test wait for the render to settle.

Run:

```sh
npm test
```

Expect **two passing suites and five passing tests**: four original tests and
the new initial-selection test. If it fails, check that All starts selected
and the controls expose `accessibilityState.selected`.

### Confirm which tasks each view contains

Replace the first import line in `Filtering.test.tsx` with:

```tsx
import { fireEvent, render, screen } from '@testing-library/react-native';
```

Immediately after the imports and before the first test, add:

```tsx
const runTitle = 'Run the app on your phone';
const completeTitle = 'Mark a task complete';
const exploreTitle = 'Explore the starter code';

async function selectFilter(name: string) {
  await fireEvent.press(screen.getByRole('button', { name }));
}
```

`fireEvent.press` triggers the control's press handler. The helper finds a
filter by its button label, so the tests don't depend on where it sits on the
screen. Append this test after the first one:

```tsx
test('shows the matching tasks without changing their status', async () => {
  await render(<App />);
  await selectFilter('Active');
  expect(screen.getByRole('button', { name: 'Active', selected: true })).toBeOnTheScreen();
  expect(screen.getByRole('button', { name: 'All', selected: false })).toBeOnTheScreen();
  expect(screen.getAllByRole('checkbox')).toHaveLength(2);
  expect(screen.getByRole('checkbox', { name: runTitle })).not.toBeChecked();
  expect(screen.getByRole('checkbox', { name: completeTitle })).not.toBeChecked();
  expect(screen.queryByRole('checkbox', { name: exploreTitle })).toBeNull();

  await selectFilter('Completed');
  expect(screen.getByRole('button', { name: 'Completed', selected: true })).toBeOnTheScreen();
  expect(screen.getByRole('button', { name: 'Active', selected: false })).toBeOnTheScreen();
  expect(screen.getAllByRole('checkbox')).toHaveLength(1);
  expect(screen.getByRole('checkbox', { name: exploreTitle })).toBeChecked();

  await selectFilter('All');
  expect(screen.getAllByRole('checkbox')).toHaveLength(3);
  expect(screen.getByRole('checkbox', { name: runTitle })).not.toBeChecked();
  expect(screen.getByRole('checkbox', { name: exploreTitle })).toBeChecked();
});

```

Run `npm test` again. Expect **two suites and six passing tests**. This catches
a correct-looking control that never changes the list's `data`, and confirms
that switching filters doesn't change task status.

### Confirm transitions and recovery from empty results

Finally, append these two tests. They reproduce the two empty-state checks
above and confirm that returning to All preserves the updated tasks:

```tsx
test('removes completed tasks from Active and preserves them in All', async () => {
  await render(<App />);
  await selectFilter('Active');
  await fireEvent.press(screen.getByRole('checkbox', { name: runTitle }));
  expect(screen.queryByRole('checkbox', { name: runTitle })).toBeNull();
  expect(screen.getByRole('checkbox', { name: completeTitle })).not.toBeChecked();
  await fireEvent.press(screen.getByRole('checkbox', { name: completeTitle }));
  expect(screen.queryAllByRole('checkbox')).toHaveLength(0);
  expect(screen.getByText('No active tasks. Everything is complete.')).toBeOnTheScreen();
  expect(screen.getByRole('button', { name: 'Active', selected: true })).toBeOnTheScreen();

  await selectFilter('All');
  expect(screen.getAllByRole('checkbox')).toHaveLength(3);
  expect(screen.getByRole('checkbox', { name: runTitle })).toBeChecked();
  expect(screen.getByRole('checkbox', { name: completeTitle })).toBeChecked();
  expect(screen.getByRole('checkbox', { name: exploreTitle })).toBeChecked();
  expect(screen.queryByText('No active tasks. Everything is complete.')).toBeNull();
});

test('removes reopened tasks from Completed and explains an empty view', async () => {
  await render(<App />);
  await selectFilter('Completed');
  await fireEvent.press(screen.getByRole('checkbox', { name: exploreTitle }));
  expect(screen.queryByRole('checkbox', { name: exploreTitle })).toBeNull();
  expect(screen.queryAllByRole('checkbox')).toHaveLength(0);
  expect(screen.getByText('No completed tasks yet.')).toBeOnTheScreen();
  expect(screen.getByRole('button', { name: 'Completed', selected: true })).toBeOnTheScreen();

  await selectFilter('All');
  expect(screen.getAllByRole('checkbox')).toHaveLength(3);
  expect(screen.getByRole('checkbox', { name: exploreTitle })).not.toBeChecked();
  expect(screen.queryByText('No completed tasks yet.')).toBeNull();
});
```

Run the full checks:

```sh
npm run typecheck
npm run lint
npm test
```

Expect **two passing suites and eight passing tests**. If a hidden task is
lost when you return to All, check that `toggleTask` still maps over `tasks`.
If the empty-state assertions fail, check both the list prop and message text.

## Check what automated tests can't establish

On your phone, increase the system text size and check wrapping, scrolling,
and safe areas. With VoiceOver or TalkBack, check each filter's label and
selected state. Activate a task that disappears from the current view and
observe where accessibility focus moves. Mocked tests can't establish these
native behaviors.

## What you can build on

You've added one independent choice to state and derived the view from it.
There is still one task array to update if you later add task creation or
storage. Keep the tests as a starting point when changing that behavior.
